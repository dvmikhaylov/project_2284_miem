# Чек-лист: шаги алгоритма заказчика (по PDF «Оптимизация бизнес процессов»)

Соответствие текущего пайплайна требованиям из ТЗ/чата заказчика.

---

## Сделано в пайплайне

| Шаг | Описание | Где |
|-----|----------|-----|
| **1. По документу** | Чтение документа (PDF, DOCX, TXT) | `baseline/document_reader.py`, `read_documents/reader.py` |
| **2. Классифицировать документ** | Отнесение к типу документа (в промпте — косвенно через сущности) | Промпт просит сущности первого плана; отдельное поле `document_type` не выводится |
| **3. NER** | Извлечение сущностей | Один вызов OpenRouter: в промпте типы PERSON, ORG, DEPARTMENT, POSITION, SYSTEM, DOC_TYPE, LOCATION, DATE, TASK_ACTION, ISSUE_PROBLEM |
| **4. Цепочки действий** | Цепочки [кто] → [действие] → [что] | В промпте и выводе: `relation_chains`; парсим и при отсутствии `relations` строим их из `relation_chains` |
| **5. Отнести к бизнес-процессу** | Один процесс из фиксированного списка | В промпте — список из `business_processes.json`; в ответе — `business_process: { category, process }` |
| **6. Акторы с таксономией** | Не сырые PER/ORG, а actor_category, actor_subcategory, role_in_process, is_internal | Промпт и вывод: для PERSON, ORG, DEPARTMENT, POSITION, SYSTEM сохраняем поля акторов в JSON |
| **7. Формат вывода** | entities (с типами и полями акторов), relation_chains, business_process | `output/exp_llama_relations/*.json`: `entities`, `relations`, `relation_chains`, `business_process`, `statistics` |

---

## Частично / следующий шаг

| Шаг | Что нужно | Комментарий |
|-----|-----------|-------------|
| **Тип документа** | Явное поле `document_type` (служебная записка, письмо, поручение, договор…) | Можно добавить в промпт и в вывод; справочник типов — согласовать с заказчиком |
| **Срочность / критичность** | `urgency_score`, маркеры срочности в тексте | В PDF — по частоте маркеров («срочно», «в кратчайшие сроки»); можно считать правилами по тексту и добавить в вывод |
| **Скор необходимости оптимизации** | Частотность упоминаний процесса + срочность; скользящее среднее | Требует хранилища по документам/периодам и агрегатов (см. ниже) |

---

## Не реализовано (следующие этапы продукта)

| Шаг | Описание |
|-----|----------|
| **Хранилище фактов** | Таблицы: documents, entities, relations, document_process; срезы по времени для динамики |
| **Постобработка** | Очистка сущностей, дедупликация, entity linking, проверка таксономии перед записью в хранилище |
| **Агрегаты** | actor × process × time; mention_count, urgency_mean, friction_mean по процессам/акторам |
| **Скоры оптимизации** | frequency_score, criticality_score, friction_score; optimization_need_score = f(frequency, criticality, friction, trend) |
| **Мульти-процесс** | main_process + secondary_processes (сейчас — один процесс на документ) |
| **Дашборд и графики** | Heatmap actor×process, топ процессов по optimization score, тренды по времени, проблемные маркеры по процессам |

## Итог

- **Сделано:** чтение документа → один вызов LLM → NER (расширенные типы + акторы), цепочки действий, отнесение к одному бизнес-процессу; вывод в формате заказчика (entities с actor_*, relation_chains, business_process).
- **Уточнить с заказчиком:** справочник типов документов, нужен ли явный document_type в JSON.
- **Дальше по PDF:** хранилище, постобработка, агрегаты, скоры оптимизации, дашборд — отдельные задачи после фиксации JSON-схемы и потока документов.
